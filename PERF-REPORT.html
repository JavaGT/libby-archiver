T2-W1B

cfc1 page-blob decode — word-at-a-time quad swap

measured, rejected library (src/read.mjs)

Built and verified a u32 word-trick swap (view+shift/mask, plus 3 other variants) with byte-identical output on 144 adversarial fixtures (terminators at every offset, pairs gap 0..7, lengths incl. n%4!=0, U+2029 fallback path — the harness even caught a wrong-top-byte bug in the first draft before timing). Verdict: the isolated swap loop runs 1.60x faster (0.533→0.334 ms on 2.8 MB), but the swap is ~3% of the decode pipeline, so end-to-end the best variant manages only 1.01x (random blob) / 1.08x (realistic XHTML) — far under the 15% bar. Not adopted; src/read.mjs untouched; the 6-line change is documented as adopted-ready.

  • Key finding: the bench headline cfc1 number (19.4 ms) is a fixture artifact — random base64 bytes force Node’s error-tolerant slow utf8 decode, 95% of runtime; realistic ASCII page content decodes in ~3.4 ms where the swap matters even less

T2-W2C

archive --all loan pipelining + read-path manifest pre-hash

merged orchestration (bin/libby.mjs, src/archive*.mjs, src/pool.mjs)

(1) Loan pipelining: archiveAudiobook/archiveReadable split into prepareX (claim folder + open loan + decode openbook — REST round trips) and finishX (downloads + assembly); archiveLoanQueue in bin keeps exactly ONE next-loan setup in flight during the active loan’s downloads. Prefetched logs buffer and replay in loan order (transcript-equality test), a failed prefetch surfaces as that loan’s FAILED line, whoa still exits 3, and the composed single-loan exports are preserved for the library API. (2) Read-path pre-hash: page bodies, assets, and the cover are sha256-hashed as they are written and fed to writeManifest’s known map alongside the EPUB digest, so the integrity pass re-reads only small sidecars; resume stays correct because only files written this run get entries.

Tradeoffs / risks:

  • pipelining only saves the LAST setup round trips × (N−1) — real-world ~0.2–0.6 s per loan given gateway RTTs; wall-clock is still dominated by downloads
  • one extra setup’s REST traffic may be wasted if the run whoa-exits before that loan becomes active (teardown on exit; acceptable, bounded to one loan)
  • the pre-hash win is re-read avoidance (files are warm in page cache just after writing) — the hashing work itself moves into the download phase rather than disappearing
  • prepare/finish is a public-API addition (additive exports; existing signatures unchanged) — noted for semver
